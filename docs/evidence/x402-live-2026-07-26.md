# Live protocol spike — x402 payment (Hedera Testnet)

Run: 2026-07-26 01:35 WEST · one uninterrupted execution.

## Three distinct parties

| Role                         | Account       | Job                                     |
| ---------------------------- | ------------- | --------------------------------------- |
| Agent (payer)                | `0.0.9708355` | Buys the beneficiary check              |
| Verification service (payee) | `0.0.9758583` | Sells it                                |
| Facilitator (fee payer)      | `0.0.9758618` | Verifies and submits; pays network fees |

The run notes record two earlier attempts rejected as `amount_mismatch` and

rejected payloads were not committed, so those failures remain operator notes
rather than reproducible evidence.

facilitator fee payer.

`0x4ae8f6192eeb90e98edd253c07d4f5b7dffd2981ddac6d247ca740312e7fd025`.

## Why it matters

The transaction establishes that an agent can buy a service through the official
Hedera x402 scheme and receive a consensus receipt, rather than treating
verification as a free API call.

## Product boundary

This is a live protocol spike, not yet an end-to-end InvoiceGuard AP receipt:

- `gate-x402-live.ts`, the raw 402 requirements, signed payment payload, and
  signed result were not committed;
- the demo uses a `0x<hex>` digest while the canonical AP protocol and admitted
  adapter require unprefixed lowercase 64-hex;
- the recorded result uses RSA while the admitted adapter requires strict
  Ed25519 facilitator and service envelopes; and
- the public transaction memo is empty, while the admitted adapter requires an
  exact request-digest memo.

The public transaction can therefore support only the live x402 transport and
payment claim. It cannot support the action-binding, signed-`MATCH`, durable
recovery, or supplier-settlement claims until a committed runner executes the
admitted adapter against the exact submitted build.
